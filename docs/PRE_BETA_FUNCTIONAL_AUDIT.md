# Setra pre-beta functional audit

Baseline: `2282c66`. Audit performed on 27 November 2026. No production data was changed, no live Stripe activity was enabled, and no paid AI requests were made.

**Decision: not ready for a public beta.** The findings below are addressed in the working tree, but need a migrated staging project and two-account/device checks before release. Desktop Chromium at mobile widths is not a physical iPhone test.

## Findings and remediation

| Priority | Finding | Resolution |
| --- | --- | --- |
| P0 | Push dispatch could send server-side requests to an unverified subscription destination. Registration could also transfer an existing endpoint to a different account. | Registration and delivery now use the same provider allowlist, existing endpoint ownership is retained, unsafe legacy endpoints are not contacted, and outbound sends have a timeout. Push links stay on the Setra origin. |
| P0 | Two devices could save different workout IDs against one planned strength occurrence, duplicating history and overwriting the completion link. | The database locks the occurrence when finishing it, preserves the winning completion and rejects a second associated completion without acknowledging the losing write. Sync recovery can compare that cloud completion, retain a local backup, or explicitly save a separate, unlinked copy. No historical rows are deleted or merged. |
| P1 | Live workout recovery rebuilt missing exercises from the source template, undoing deliberate deletions and potentially changing the workout on another device. A same-name catalogue entry could hide the ID of a user-owned or coach-copied exercise. | Resume uses the saved draft snapshot. Catalogue loading retains saved exercise IDs, so existing workout and template links still resolve. |
| P1 | Formal coach feedback failed at the notification write due to a SQL name collision. | The feedback RPC now saves one record and its notification atomically and retains active relationship checks. |
| P1 | A failed or forced Adaptive Weekly Review could cause repeated paid requests, including empty weeks or arbitrarily old weeks. Its notification bypassed category settings. | Generation is limited to the latest closed configured week with training, with at most four attempts per week and an atomic claim. Previous saved reviews remain readable. Notifications use the existing preference-aware writer. |
| P1 | A stale resume record could take precedence over an explicit notification or other deep link. Profile accepted edits during loading or saving that could then be overwritten. Sign-out could stall waiting for push cleanup. | Explicit links take precedence; short resumes also cover notifications and coaching, and foregrounding does not dismiss a live workout. Profile editing waits for the baseline and current save; push cleanup cannot indefinitely block sign-out. |
| P1 | Rendering a PNG before calling native share could exhaust Safari's short tap-to-share window, leaving Save and Share unusable on slower devices. | Keeps the rendered file available for a fresh tap without rendering twice; if native sharing cannot open, offers a PNG download. Rendering errors/timeouts restore the controls. This follows [WebKit's user-activation guidance](https://webkit.org/blog/13862/the-user-activation-api/); the iPhone Photos flow still needs device verification. |
| P2 | A clean lint result depended on whether ignored local utilities were present. Two existing test suites were not run by the reliability command. | Ignore disposable utilities and browser output; include Profile and safe-redirect tests in reliability. |
| P2 | Notification pagination uses a timestamp-only cursor. A page boundary with multiple identical timestamps can omit notifications from subsequent pages. | Open. Use a timestamp-plus-ID cursor when addressing this. |
| P2 | Share preview and PNG are laid out by different renderers. Passing bounds and alpha tests does not prove pixel-for-pixel parity, particularly for long names and crops. | Open. Confirm acceptable parity on iPhone before enabling any changes to the share layouts. |
| P3 | Retaining legacy exercise IDs can result in identical names in the exercise picker. | Open. Disambiguate presentation without changing history IDs. |

187 automated checks passed on Node 22. All 25 Chromium tests passed against a local preview with no Supabase credentials; only the local training journey uses the full training UI without mocked endpoints. Seven SQL suites passed after replaying 65 migrations in a disposable PostgreSQL-compatible PGlite database with minimal Supabase auth roles/settings. The hosted scheduler migration (Cron, Vault and network extensions) did not run there. This does not replace testing actual Supabase API grants, RLS and Realtime from real sessions.

Push provider allowlists follow the documented endpoints for [Safari](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [Chrome](https://developer.chrome.com/blog/push-notifications-on-the-open-web), [Firefox](https://blog.mozilla.org/services/2016/08/23/sending-vapid-identified-webpush-notifications-via-mozillas-push-service/) and [Windows push](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/migrate-to-windows-app-sdk/guides/notifications). Test real device subscriptions in staging; a shared device may need push disabled and re-enabled after changing accounts.

## Exact staging and iPhone retest

1. **Before using a staging app:** confirm the earlier Adaptive and billing migrations are applied, back up staging, and apply the four audit migrations below in order. Use fresh Free, Premium and Adaptive athletes and an active coach with an individual plan. Keep a separate unrelated account to test isolation. Keep Stripe keys in test mode.
2. **Free onboarding and profile:** create a Free athlete, confirm email, reopen from the callback, and complete onboarding. Open Profile and leave without edits: no warning. Change then revert a setting: no warning. Change and save it: reopen on the second device and confirm it persisted. Verify password reset through the staging origin.
3. **iPhone live strength and sync:** plan one strength session for today. Enter sets/RPE, drag a long-named exercise down, then delete an exercise with entered data. Background for five seconds, reopen, then fully reload. Confirm the deleted exercise stays absent and the other sets keep their values. Finish with both time fields visible and editable. Open History: exactly one session. On two devices, start the same planned workout independently, finish while offline, then reconnect in opposite order. Confirm one planned completion, a recoverable device copy and no endless retry; choose Use cloud and verify the backup. Repeat while editing the same workout rather than starting separately.
4. **iPhone navigation and sharing:** background from Notifications, a coach week and a live workout. Resume at five seconds, two minutes and more than five minutes. Open a notification link after a long absence: it should open its target, not Today. Open a workout and PB share tile, switch Full/Compact, choose a large photo, cancel, select and replace the photo, then Save and use Share. Verify Photos, no stuck overlay, and transparent PNG corners.
5. **Coach, coached athlete and friend:** accept the coaching invitation and assign a mixed program and a group workout. Reschedule one unstarted session, then complete it as the athlete with RPE and feel. Verify the coach sees the same result, can leave feedback and a weekly note, and the athlete can reply. The unrelated account must see nothing. Ending the relationship must block new assignments or replies while the athlete retains history. Separately test a friend request, the completed-workout privacy toggle and a shared workout's sets/load.
6. **Notifications, Adaptive and billing:** on the installed iPhone app, allow push, verify a timed reminder moves or cancels when the workout is moved or completed, and test two devices and disabled categories. Verify Premium opens analytics but not Adaptive; generate an Adaptive review once, repeat the request, ask a follow-up, and approve/undo an eligible personal change while a coached session is protected. Use Stripe test Checkout and Portal to verify billing transitions, webhook replay, the seat limit and independent athlete access after a coach downgrade.
7. **External files:** import a known FIT, TCX or GPX activity, repeat the same file, and reconcile with a manual entry without duplicating or overwriting it. Confirm the planned match and resulting PB or History entry on the second device.

## Changes and rollout

- `20261127000600_protect_weekly_review_generation.sql`: review attempts and the server-only notification grant.
- `20261127000700_restrict_push_subscription_destinations.sql`: validated provider endpoints and subscription ownership.
- `20261127000800_guard_strength_occurrence_completion.sql`: one linked strength completion per occurrence for new writes.
- `20261127000900_fix_coach_feedback_notification_write.sql`: repairs the coach feedback transaction.

Application changes are in Home and Profile, Adaptive review, notification delivery and the service worker, navigation, share export, exercise catalogue and sync errors. Tests are in `lib/**/*.test.ts`, `tests/*.sql` and `tests/browser/`. The added local-strength browser test uses `SETRA_E2E_LOCAL_ONLY=1` against a separate preview with no Supabase credentials.

**Remaining release gates:** apply and verify the audit migrations on staging; pass the physical iPhone and multi-account checks; verify staged Stripe and push only if exposed to beta users; approve the [public beta support, privacy and deletion process](./PUBLIC_BETA_DEPENDENCIES.md). No new environment variables or Vercel scheduling changes are required.
